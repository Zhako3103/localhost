# Разбор Rust-проекта localhost: HTTP-сервер на epoll

Nov 3, 2026 · @zhako

## 1. Общая картина

**localhost** — это самописный HTTP/1.1-сервер на Rust: один поток, один `epoll`, ни одной внешней зависимости кроме `libc`. Он умеет раздавать статические файлы, показывать содержимое каталогов, делать редиректы, принимать загрузку файлов (`multipart/form-data`), удалять файлы (`DELETE`), запускать CGI-скрипты (Python/Perl), вести cookie-сессии и обслуживать несколько «виртуальных хостов» на одних портах. Настройки читаются из файла в стиле nginx (`config/default.conf`).

### Дерево Rust-файлов

```text
src/
├── main.rs              точка входа: читает конфиг, создаёт Server, запускает цикл
├── lib.rs               объявляет модули крейта
├── config.rs            парсер и валидатор конфигурации
├── sys.rs               тонкие обёртки над libc (весь unsafe проекта — только здесь)
├── session.rs           хранилище сессий в памяти
├── router.rs            «что делать с этим запросом?» (выбор сервера и маршрута)
├── server.rs            реактор: epoll-цикл и конечный автомат каждого соединения
├── http/
│   ├── request.rs       инкрементальный парсер HTTP-запроса
│   └── response.rs      сборка ответа, коды статусов, страницы ошибок, MIME
└── handlers/
    ├── static_files.rs  отдача файлов, листинг каталога, страницы ошибок
    ├── upload.rs        multipart, сохранение файлов, DELETE
    └── cgi.rs           запуск CGI-процессов через неблокирующие pipe
```

Каталоги `www/`, `tests/`, `cpp/`, `docs/` — не Rust: `www/` — сайт для демонстрации (HTML, CSS, JS, CGI-скрипты на Python/Perl), `tests/` — Python-тесты, `cpp/` — та же идея на C++.

### Главная идея: «реактор»

Обычный сервер на каждое соединение создаёт поток, который сидит и ждёт данных. Здесь всё иначе: **один** поток вызывает `epoll_wait` — системный вызов «усни, пока хоть какой-то сокет не станет готов». Когда ядро говорит «сокет №7 можно читать», сервер делает **ровно один** `read` на нём, продвигает состояние этого соединения и возвращается к `epoll_wait`. Никто никогда не блокируется на чтении или записи — поэтому один поток обслуживает тысячи клиентов.

### Путь одного запроса (по шагам)

1. `main.rs` загружает конфиг → `Server::new` открывает слушающие сокеты и регистрирует их в epoll.
2. Клиент подключается → `accept` создаёт структуру `Conn` (состояние соединения).
3. Приходят байты → `Parser::feed` (в `request.rs`) копит их и возвращает `NeedMore`, `Head`, `Done` или `Err(код)`.
4. Как только разобраны заголовки (`Head`), `on_head` выбирает виртуальный хост и маршрут, ставит лимит размера тела, отвечает на `Expect: 100-continue`, и может сразу отклонить запрос (413, 405) — не дожидаясь тела.
5. Когда пришёл весь запрос (`Done`) — `handle_request` смотрит на результат маршрутизации (`Action`) и вызывает нужный обработчик: файл, листинг, загрузка, удаление, сессия, редирект или CGI.
6. Готовый `Response` кладётся в буфер вывода (`queue_response`), сокет переключается на ожидание `EPOLLOUT` (можно писать).
7. `on_writable` отправляет кусок за куском (файлы читаются по 64 КиБ), затем `response_done` либо закрывает соединение, либо возвращается в `Reading` (keep-alive).
8. Раз в 250 мс `sweep` закрывает просроченные соединения и удаляет протухшие сессии.

### Rust-приёмы, которые встречаются везде

- **`enum` с данными** — `Action`, `Progress`, `State`, `Method::Other(String)`: вместо флагов и «магических чисел» состояние выражено типом, а `match` обязывает обработать все варианты.
- **`Result<T, E>` и оператор `?`** — ошибка либо возвращается наверх, либо превращается в HTTP-код (`.map_err(|_| 400u16)?`).
- **`Option`** — вместо `null`: «может быть, а может не быть».
- **`Rc<Config>`** — конфиг один, но нужен в нескольких местах; `Rc` — счётчик ссылок для однопоточного кода (`clone()` копирует только указатель).
- **«Вынуть из карты — поработать — вернуть»** — в `server.rs` соединение временно удаляется из `HashMap` (`self.conns.remove`), чтобы можно было одновременно держать `&mut Conn` и `&mut self`; borrow checker иначе не позволил бы. После работы `finish` вставляет его обратно.
- **`catch_unwind`** — если в обработчике случится паника, она ловится и убивает только одно соединение, а не весь сервер.
- **`impl Drop`** — автоматическая уборка: `Epoll` закрывает fd, `CgiJob` убивает и «пожинает» процесс.

## 2. Cargo.toml, main.rs, lib.rs, mod.rs

### Cargo.toml

```toml
[package]
name = "localhost"
version = "0.1.0"
edition = "2024"

[dependencies]
libc = "0.2.191"
```

- `name = "localhost"` — имя пакета. Из-за этого в `main.rs` пишут `use localhost::...` — библиотечный крейт тоже называется `localhost`.
- `edition = "2024"` — редакция языка Rust (набор правил синтаксиса и поведения).
- `libc` — единственная зависимость: привязки к C-библиотеке системы (`epoll_*`, `fcntl`, `getrandom`, ...). Всё остальное — только стандартная библиотека `std`.

### lib.rs (7 строк)

```rust
pub mod config;
pub mod handlers;
pub mod http;
pub mod router;
pub mod server;
pub mod session;
pub mod sys;
```

Каждая строка `pub mod имя;` говорит компилятору: «возьми файл `src/имя.rs` (или `src/имя/mod.rs`) и сделай его модулём». `pub` — модуль виден снаружи крейта (нужно, чтобы `main.rs` и тесты могли их использовать). Проект разделён на **библиотеку** (`lib.rs`) и **бинарник** (`main.rs`) — так удобно тестировать логику отдельно.

### handlers/mod.rs и http/mod.rs

- `handlers/mod.rs`: `pub mod cgi; pub mod static_files; pub mod upload;` — перечисляет три обработчика папки `handlers/`.
- `http/mod.rs`: `pub mod request; pub mod response;` — то же для папки `http/`.

Файл `mod.rs` — «вход» папки-модуля. Без него компилятор не узнает о файлах внутри папки. Потом в коде пишут пути вида `crate::http::request::Parser`.

### main.rs (21 строка)

| Строки | Что делает |
| --- | --- |
| 1–2 | `use` подключает типы `Config` и `Server` из библиотеки `localhost`. |
| 4 | `fn main()` — точка входа программы. |

## 3. sys.rs — обёртки над libc (136 строк)

Всё `unsafe` проекта живёт только здесь. `unsafe` — блок, внутри которого разрешено вызывать C-функции: компилятор не может проверить их безопасность, поэтому проверку берёт на себя автор. Каждый блок снабжён комментарием `// SAFETY:` — почему тут всё безопасно. Снаружи модуль предоставляет обычные «безопасные» функции.

### Константы и типы (строки 7–20)

- `EPOLLIN`, `EPOLLOUT`, `EPOLLERR`, `EPOLLHUP` — битовые флаги событий epoll: «можно читать», «можно писать», «ошибка», «собеседник повесил трубку». В `libc` они имеют тип `i32`, поэтому здесь они переводятся `as u32` — тип поля `events` в структуре.
- `pub struct Epoll { fd: RawFd }` — обёртка над файловым дескриптором epoll-объекта. `RawFd` — просто `i32`.
- `pub type Event = libc::epoll_event` — псевдоним типа, чтобы остальной код не зависел от `libc` напрямую.
- `empty_event()` — пустая запись `{events: 0, u64: 0}`; нужна для инициализации массива событий (`vec![empty_event(); 512]`). Поле `u64` — «произвольные данные пользователя»; здесь в нём лежит номер fd, чтобы после `epoll_wait` понять, какой сокет готов.

### impl Epoll (строки 22–64)

| Функция | Что делает |
| --- | --- |
| `new()` | `epoll_create1(EPOLL_CLOEXEC)` создаёт epoll-объект. `CLOEXEC` — дескриптор не «протечёт» в дочерние CGI-процессы. При `fd < 0` возвращается `io::Error::last_os_error()` (чтение `errno`). |
| `ctl(op, fd, events)` | Приватный общий вызов `epoll_ctl`. Формирует `epoll_event`, где `u64 = fd`, и передаёт ядру указатель на него. Код возврата `< 0` → `Err`. |
| `add` / `modify` / `delete` | Тонкие обёртки: `EPOLL_CTL_ADD` (начать следить за fd), `EPOLL_CTL_MOD` (сменить набор интересующих событий), `EPOLL_CTL_DEL` (перестать следить). |
| `wait(events, timeout_ms)` | **Единственная блокирующая точка сервера.** Передаёт ядру изменяемый срез `&mut [Event]` — ядро заполняет его готовыми событиями и возвращает их число. Если вызов прерван сигналом (`Interrupted`) — это не ошибка, возвращается `Ok(0)` и цикл просто идёт дальше. `timeout_ms` — сколько максимум ждать; это нужно для таймеров. |

`impl Drop for Epoll` (строки 66–71) закрывает дескриптор при уничтожении объекта — типичный RAII-паттерн Rust: ресурс освобождается автоматически, когда владелец выходит из области видимости.

### Остальные функции

- **`set_nonblocking(fd)`** (73–85) — читает текущие флаги дескриптора (`F_GETFL`) и добавляет `O_NONBLOCK` (`F_SETFL`). После этого `read`/`write` не засыпают, а возвращают ошибку `WouldBlock`, если данных нет. Применяется к pipe-ам CGI.
- **`ignore_sigpipe()`** (87–92) — если писать в сокет, который клиент уже закрыл, система по умолчанию убьёт процесс сигналом SIGPIPE. Здесь сигнал игнорируется, и `write` просто вернёт ошибку.
- **`raise_nofile_limit()`** (95–109) — поднимает «мягкий» лимит открытых файлов (`RLIMIT_NOFILE`, обычно 1024) до «жёсткого» максимума и возвращает итоговое значение. Каждое соединение = один fd, поэтому это ограничивает число клиентов. При ошибке возвращается дефолт 1024.
- **`listen(addr)`** (112–120) — `TcpListener::bind` (в `std` уже включает `SO_REUSEADDR`, так что перезапуск не ждёт таймаута порта), затем `set_nonblocking(true)`, а потом повторный `libc::listen(fd, 4096)`, который увеличивает очередь непринятых соединений (backlog) до 4096.
- **`kill(pid, sig)`** и константа `SIGKILL` — отправка сигнала процессу (в коде сейчас для остановки CGI используется `Child::kill` из `std`).
- **`random_bytes(buf)`** (132–136) — `getrandom` заполняет буфер криптографически стойкими случайными байтами ядра. Возвращает `true`, если заполнено всё. Нужно для идентификаторов сессий и имён загружаемых файлов.

## 4. config.rs — чтение и проверка конфигурации (613 строк)

Превращает текст вида `server { ... route / { ... } }` в дерево структур Rust. Два этапа: `Config::parse` проверяет синтаксис и всё, что не требует диска; `Config::resolve_paths` проверяет, что файлы и каталоги существуют, и делает пути абсолютными. `Config::load` делает оба.

### Пример файла config/default.conf

Два блока `server`. Первый слушает `127.0.0.1:8080` и `:8081` (имя `localhost`), второй — тот же порт 8080, но с именем `second.local`: это виртуальный хост (сервер выбирается по заголовку `Host`). Внутри — `route`-блоки: `/` (статика + сессия), `/files` (autoindex), `/upload` (GET/POST/DELETE), `/small` (лимит тела 100 байт), `/cgi-bin` (расширения `.py`/`.pl`), `/session` (встроенный обработчик), `/old` (редирект 301).

### Строки 1–31: ошибки

- `DEFAULT_MAX_BODY` = 1 МиБ, `MIN_BODY` = 1 байт, `MAX_BODY` = 100 МиБ — границы размера тела запроса.
- `struct ConfigError(pub String)` — «кортежная структура» из одного поля — текста ошибки. `#[derive(Debug, Clone, PartialEq)]` автоматически генерирует копирование, сравнение и отладочный вывод.
- `impl fmt::Display` — как печатать ошибку человеку (`{}`); `impl std::error::Error` — пометка, что это настоящий тип ошибки.
- `fn err<T>(msg: impl Into<String>) -> Result<T, ConfigError>` — утилита: вернуть `Err(…)` одной короткой записью. Дженерик `<T>` позволяет использовать её в функциях с любым типом успеха; `impl Into<String>` — принимает и `&str`, и `String`.

### Строки 33–106: данные

| Тип | Поля и смысл |
| --- | --- |
| `enum Handler { Session }` | Встроенный обработчик. Сейчас один, но `enum` легко расширить. |
| `struct Route` | Один маршрут: `path` (префикс URL), `methods`, `root` (каталог на диске), `index` (имя индексного файла), `autoindex` (показывать ли список файлов), `redirect` (`Option<(u16, String)>` — код и куда), `cgi` (список пар «расширение → интерпретатор»), `upload_dir`, `max_body` (свой лимит маршрута), `handler`, `session` (вести ли сессию). |
| `struct ServerConfig` | Один `server { }`: `host` (`Ipv4Addr`), `ports`, `server_names`, `max_body`, `error_pages` (`HashMap<u16, PathBuf>`), `routes`. |
| `struct Config` | Вся конфигурация: `Vec<ServerConfig>`. |
| `struct ListenerSpec` | «Один сокет, который надо открыть»: host + port + индексы серверов, которые на нём отвечают (в порядке объявления). |

- `Route::new(path)` (54–68) — конструктор с разумными значениями по умолчанию: разрешён только GET, остальное выключено.
- `Route::allows(&self, m)` (70–75) — разрешён ли метод. `HEAD` считается разрешённым, если разрешён `GET` (по стандарту HEAD = GET без тела).
- `Route::cgi_for(&self, file_name)` (77–82) — ищет в `cgi` расширение, с которым заканчивается имя файла, и возвращает путь к интерпретатору. Условие `file_name.len() > ext.len()` исключает файл с именем просто `.py`. Возвращает `Option<&str>` — ссылку на данные внутри `Route`, без копирования.

### Строки 108–172: токенизатор

`tokenize(text)` разбивает текст на «слова» (токены). Проходит по символам: `{`, `}` и `;` — это отдельные токены (перед ними сохраняется накопленное слово), пробелы завершают слово, остальное накапливается в `cur`. `std::mem::take(&mut cur)` забирает строку и оставляет в `cur` пустую — без лишнего копирования. Пример: `ports 8080 8081;` → `["ports", "8080", "8081", ";"]`.

`struct Tokens { toks, pos }` — токены и текущая позиция чтения. Методы:

- `peek()` — посмотреть следующий токен, не сдвигаясь.
- `next()` — взять следующий токен и сдвинуться.
- `expect(want)` — взять токен и проверить, что он равен ожидаемому (например `{`); иначе — ошибка «ожидалось X, найдено Y».
- `args(name)` — собирает аргументы директивы до `;`. Если встретили `{`/`}` или конец файла — ошибка «пропущена `;`».

### Строки 174–293: парсинг маршрута

- **`parse_size(s)`** — «10m» → 10 485 760, «2k» → 2048, «100» → 100. Смотрит на последний символ: `k/K` или `m/M` → множитель, цифры — срез без суффикса. `checked_mul` проверяет переполнение (вернёт `None`, если число слишком большое).
- **`check_body_size(n)`** — проверяет, что `1 <= n <= 100 МиБ`.
- **`one(name, args)`** — убеждается, что у директивы ровно один аргумент, и возвращает ссылку на него. Параметр `'a` — «время жизни»: обещание компилятору, что возвращаемая ссылка живёт не дольше массива `args`.
- **`parse_route(t, path)`** — цикл чтения директив до `}`. Для каждой: `methods` (GET/POST/DELETE, дубликаты отбрасываются), `root`, `index`, `autoindex on|off`, `session on|off`, `redirect код цель` (только 301/302/303/307/308), `cgi .расш интерпретатор`, `upload_dir`, `client_max_body_size`, `handler session`. Неизвестная директива → ошибка. В конце: у маршрута должны быть `root`, `redirect` или `handler`, иначе он бессмыслен. Многие ветки типа `"on" => true, "off" => false, o => return err(...)` — это `match` над строкой с веткой «всё остальное» для сообщения об ошибке.

### Строки 295–374: parse\_server

Создаёт `ServerConfig` со значениями по умолчанию (host `0.0.0.0`, лимит 1 МиБ). Далее цикл директив:

- `route <path> { ... }` — вызывает `parse_route`; дубликат пути → ошибка. `continue` возвращает к началу цикла.
- `host` — `localhost` превращается в `127.0.0.1`, иначе строка парсится как IPv4.
- `ports`/`port` — парсится в `u16` (автоматически отсекает >65535), порт 0 и повторы запрещены.
- `server_name` — `extend` добавляет все аргументы (имён может быть несколько).
- `client_max_body_size`, `error_page <код 4xx/5xx> <файл>`.

Если портов нет — ошибка.

### Строки 376–489: impl Config

- **`parse(text)`** — токенизирует; пока есть токены, ожидает слово `server` и вызывает `parse_server`. Пустой конфиг — ошибка. После разбора — `check_conflicts`.
- **`check_conflicts()`** — два сервера не могут слушать один и тот же `host:port` с одинаковым `server_name`. Также нельзя сочетать `0.0.0.0:порт` с конкретным адресом на этом же порту (остальное оставлялось бы в `bind` ошибкой «адрес занят»). `names_of` для сервера без имён возвращает `[""]`, так что два безымянных сервера тоже конфликтуют.
- **`resolve_paths()`** — для каждой страницы ошибок, `root`, `upload_dir`: `fs::canonicalize` делает путь абсолютным, разворачивает симлинки и попутно проверяет существование. Это важно для безопасности: позже роутер сравнивает канонические пути и не пустит за пределы `root`. Интерпретаторы CGI проверяются на существование.
- **`load(path)`** — `read_to_string` + `parse` + `resolve_paths`.
- **`listeners()`** — группирует: для каждой пары `(host, port)` создаёт один `ListenerSpec`, а если на этот адрес смотрит несколько серверов — добавляет их индексы в список. В `default.conf` результат: два сокета (8080 с двумя серверами, 8081 с одним).

### Строки 491–613: тесты

`#[cfg(test)] mod tests` компилируется только при `cargo test`. Проверяют валидный конфиг, группировку виртуальных хостов, конфликты, границы размера, синтаксические ошибки, неправильные маршруты, несуществующие пути и суффиксы размеров. `.unwrap()` в тестах — норма, падение = провал теста.
